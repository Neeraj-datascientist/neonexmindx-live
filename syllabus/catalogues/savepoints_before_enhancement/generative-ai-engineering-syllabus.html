Important Notice: Generative AI Practical Crash Course Exemption

Note for Enrolled Candidates: Candidates enrolled in this comprehensive Generative AI Engineering Master Program do not need to take the separate introductory Generative AI Practical Crash Course. Because this degree-level curriculum includes in-depth Generative AI Foundation in Part A, joint Advanced LLM and RAG modules in Part B, and 11 specialized enterprise modules in Part C (Stateful Agents, MCP, Fine-Tuning, Security Red Teaming & LLMOps), all introductory crash-course material is superseded by deep-dive practical engineering.

AI Foundation

1 week
Module Purpose & IntentEstablish the shared AI vocabulary and system lifecycle used throughout the Neonex Mindx programmes.

Core concepts

  • What is Artificial Intelligence?
  • AI vs Machine Learning vs Deep Learning vs Generative AI.
  • Major areas of AI and types of AI systems/problems.
  • Predictive/discriminative systems versus generative systems; rule-based, statistical, ML and LLM-driven approaches.

System and professional context

  • AI lifecycle and AI system development lifecycle.
  • Role of an AI Engineer and relationship to Data Analyst, Data Scientist, Data Engineer, ML Engineer and GenAI Engineer roles.
  • Modern AI ecosystem and where data, models, prompts, tools, applications and deployment fit.
  • Responsible AI fundamentals: privacy, fairness/bias awareness, reliability, transparency and human oversight.
Practical Lab / Guided StudioMap three real problems to the appropriate method (analytics, classical ML, deep learning or GenAI), then explain why a different approach may be more suitable.
Expected DeliverableAI foundation assessment and a one-page AI-system lifecycle map.
Progression Gate / Exit CriteriaCan explain the main AI categories, describe a simple AI project lifecycle and select a sensible first approach to a problem.
Pathway Integration & ContextShared with relevant programmes. This block is not a separate GenAI-only orientation; GenAI examples are included inside the same class.

Advanced LLM Engineering

3 weeks
Module Purpose & IntentThis is the most important shared advanced module: it follows NLP/Transformers and covers reliable LLM system engineering rather than only prompt use.

LLM architecture and selection

  • Transformer architecture and attention intuition.
  • Pretraining vs instruction tuning.
  • Inference, model selection and model capability assessment.

Context engineering

  • What information the model receives.
  • Context assembly, selection, prioritization and context windows.
  • Conversation history, retrieved context and tool definitions.
  • Context budgeting, long-context management and context compression.

Harness, loop and graph engineering

  • Harness: agent/runtime environment, tools, execution environment, permissions, sandboxing, guardrails, verification, state/memory integration and error handling.
  • Loop engineering: observe, decide, act, receive result, re-evaluate, repeat; stop conditions, retries and recovery.
  • Graph engineering: nodes, edges, state transitions, conditional branches, parallel paths, joins, cycles and explicit workflow topology.

LLM application engineering

  • Structured/JSON outputs and schema validation.
  • Function calling/tool calling, model routing, provider abstraction and fallback models.

Reliability and performance

  • Retries, timeouts, fallback, validation and error handling.
  • Streaming, batching, caching, token/cost/latency optimization.

Open-source LLM and modern model awareness

  • Hugging Face, open-source/open-weight models, model selection and licensing.
  • Ollama and local inference; vLLM and efficient inference awareness.
  • Reasoning models vs standard generation; multimodal LLMs, vision-language models, audio-enabled models, computer-use/action-oriented models, small language models and efficient inference.
Practical Lab / Guided StudioBuild or refactor an LLM service using context budgets, structured outputs, provider abstraction, controlled tools and traces. Include at least one failure test (invalid structured output, provider failure or budget limit) and explain the harness/loop/graph decisions.

1 week

Threat modelling

                Part C & D: Technical Defense & Assessment Rubric

                Every candidate must demonstrate live working software, answer architecture questions, and present observable evidence.

                Evaluation Framework
                Review Dimension What Independent Reviewers & Technical Panel Verify
                1 · Correctness and requirement fit The implementation matches stated behavior, data boundaries and acceptance criteria; no unsupported capability is claimed.
                2 · Engineering structure Components, contracts, configuration, repository and documentation are understandable and maintainable.
                3 · Verification evidence Tests cover successful paths and relevant failure/negative cases; results are reproducible and changes are compared where applicable.
                4 · Security and responsibility Permissions, secrets, data handling, tool boundaries and human review are designed and tested where relevant.
                5 · Operations and trade-offs The candidate can explain recovery, observability, versioning, limitations, cost/latency considerations and rollback where relevant.
                6 · Technical communication The candidate demonstrates the system, walks through artifacts, explains key decisions and distinguishes measured results from assumptions.

                Quick Technical Glossary

                Core terms and operational definitions applied across the curriculum.

                Term / Acronym Operational Meaning & Industry Context
                A2A Agent-to-agent interoperability: patterns for agents/services to discover or communicate with one another.
                ADR Architecture Decision Record: a concise record of a significant design choice, alternatives and consequences.
                API Application Programming Interface: a contract through which software components communicate.
                ASR / TTS Automatic Speech Recognition converts speech to text; Text-to-Speech converts text to audio.
                Idempotency A retry or repeated request does not unintentionally duplicate a state change or external side effect.
                LLMOps Operational practices for versioning, evaluating, deploying, observing and improving LLM-based systems.
                MCP Model Context Protocol: a protocol for connecting AI applications with external tools and context resources.
                OCR Optical Character Recognition: extracting text from images or scanned documents.
                PEFT Parameter-Efficient Fine-Tuning: adaptation methods that update a smaller parameter subset or adapter rather than all model weights.
                PII Personally Identifiable Information: data that identifies or can reasonably be linked to a person.
                QLoRA / LoRA Parameter-efficient adaptation approaches; QLoRA combines quantization with LoRA-style adapters.
                RAG Retrieval-Augmented Generation: retrieving relevant evidence and supplying it as context for generation.
                VLM Vision-Language Model: a model that processes image/visual content alongside language.
                Release gate A defined set of checks or thresholds that must pass before a version is released.
                Tenant isolation Controls preventing one customer/account’s data or permissions from leaking into another tenant’s context or results.
