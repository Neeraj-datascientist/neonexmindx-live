02 · How cohorts are taught

Shared teaching is an operational design, not a label

To avoid duplicate delivery, the timetable should be managed by shared module IDs and common exit criteria. A module is shared only when learning outcomes, depth, hands-on activity and assessment are equivalent.

PART A

All relevant course cohorts

Use the already approved common module and its lesson order. Candidates may have role-specific examples, but the same shared teacher/session and baseline assessment should be used where outcomes match.

  • No second Python basics.
  • No second common SQL or Git course.
  • No re-writing common math/ML modules merely to change the course name.
PART B

AI Engineering + GenAI Engineering

These two cohorts stay together for the full AI Engineering Modules 14–23 in the same sequence. GenAI-specific lab scenarios can add context, but the shared core module is not omitted or reduced.

  • Shared advanced engineering standards.
  • Same module objectives and core assessment.
  • Small optional GenAI-specific challenge where it adds context, not duplicate teaching.
PART C

GenAI Engineering only

Dedicated specialist teaching time goes to the areas that differentiate a GenAI engineer after completing the common and AI Engineer advanced core: enterprise RAG operations, stateful agents, connected tool protocols, product architecture, evaluation/security, inference/LLMOps and focused multimodal work.

  • Build on prior work rather than repeat it.
  • Require evidence of reliability and safe operation.
  • Keep elective/GPU-intensive work optional where infrastructure dictates.

How the training operations should work

  1. Common module register: give every approved shared module a canonical code, version, lesson plan, hours, assessment rubric and pass record.
  2. Enrollment mapping: record which programmes share each module; only compatible cohorts attend together.
  3. Joint Part B calendar: AI Engineering and GenAI Engineering use the same M14–M23 timetable, instructor sessions and core grading criteria.
  4. Specialist lab differentiation: when useful, provide separate application context after the common explanation—e.g., model inference pipeline for AI Engineers and document/embedding lifecycle for GenAI Engineers—without removing shared core learning.
  5. Credit and remediation: learners already passed on an equivalent module can receive credit after an evidence check; candidates who have gaps take remediation before the next dependency.
  6. Content governance: when the canonical common module changes, revise each dependent programme map rather than silently fork the content.

06 · Why Part C is the differentiator

Part C is not another introduction—it is where candidates engineer dependable GenAI products

The primary roadmap already introduces APIs, LangChain, memory, embeddings, vector databases, RAG, agents, Agentic AI, n8n and portfolio applications. Part A puts the baseline on the same AI Engineering path, Part B gives the shared advanced engineering depth, so Part C intentionally focuses on the harder application of that knowledge.

Recommended learning sequence inside Part C

Each stage builds on Part A/B. The detailed module catalogue below remains the authoritative topic-level syllabus.

Enterprise knowledge lifecycle → stateful agent → MCP/A2A integration → product/API experience.

Agent and integration

Model and modality

Model/license selection memo plus a controlled adaptation experiment or multimodal mini-app, with limitations stated.

Architecture defense

Architecture diagram, ADRs, acceptance criteria and one tabletop failure drill tied to the selected Part D project.

Design rules that keep Part C balanced

  1. Extend, do not duplicate: use shared M22/M23 theory; spend specialist time on systems, tests, data lifecycle, deployment and failure cases.
  2. One deep stack, alternatives by comparison: select one main LLM provider route, one open/local route, one primary vector store, LangGraph for stateful agent work and n8n for the main automation lab. Compare alternatives when useful; do not require deep mastery of every framework.
  3. Projects must produce evidence: each specialist module contributes code, test cases, architecture, traces, evaluation or operational notes to the final capstone.
  4. Keep hardware risk bounded: fine-tuning/LoRA/QLoRA is a controlled guided lab; lack of GPU access should not prevent candidates from learning model-choice judgement and evaluation.
  5. Teach modern terms as engineering decisions: MCP, A2A, agentic RAG, multimodal models and inference serving must have a clear use case, trade-off and test—not merely appear in a list.
07 · Part D — project studio and capstone

Seven project choices based on the competitor landscape—designed to a higher evidence standard

Competitor pages commonly highlight an enterprise document Q&A/RAG project, a tool-using or multi-agent system, automation, multimodal/voice use cases, fine-tuning/open models and a final capstone. Part D incorporates these themes, but every project requires test/evaluation evidence, source/code ownership, security thinking and operational documentation.

Recommended project strategy: candidates do small builds earlier (AI productivity, LLM API app and shared RAG baseline), then select one Part D flagship project. The flagship should reuse earlier artifacts and evolve them—do not restart from scratch only in the final month.

Minimum acceptance criteria for any flagship project

Functional

Clear use case, working main flow, defined inputs/outputs and documented limitations.

Engineering

Version-controlled code, setup instructions, modular structure, basic automated tests and configuration/secrets handled safely.

Quality & trust

Evaluation set, failure examples, security/threat assessment, data permissions and human review boundaries.

Production

Deployed or reproducibly runnable demo, basic logs/traces, cost/latency note and failure/rollback instructions.

Ownership

Candidate can explain design, tools, critical code paths, licenses, evaluation results and trade-offs live.

Portfolio-ready

README, architecture diagram, demo script, test report, known issues, screenshots/results and a clear project narrative.

08 · Programme quality gates

Progression requires observable evidence

Shared modules use their approved assessments. Additional GenAI gates assess whether the candidate can safely and reliably apply shared learning to a GenAI product.

GATE A · FOUNDATION

Part A completion

Passed approved foundational assessments, clean repository practices, demonstrable Python capability and a conceptual understanding of AI/GenAI.

GATE B · ADVANCED CORE

Part B completion

Joint AI Engineering core artifacts: advanced Python component, AI data-flow/design artifacts, an LLM application, and an advanced RAG design/experiment.

GATE C · SPECIALIZATION

Part C completion

Enterprise RAG operations, bounded stateful agent, GenAI evaluation/security report, an integration/tool workflow and LLMOps evidence.

GATE D · PROJECT

Capstone defense

Functional flagship product, tests/evaluation, threat model, architecture, runbook and a live technical defense.

REMEDIATION

Close gaps early

Do not allow repeated foundation gaps to accumulate into a capstone failure. Use diagnostics, clinics and resubmissions with clear rubrics.

HONEST OUTCOME

Evidence, not promises

Course completion should not be advertised as guaranteed employment, guaranteed salary or research-scientist readiness. Show actual projects and assessed competency.
